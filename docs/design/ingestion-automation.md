# 取り込みの自動化

- 状態: 実装済み（実行層は 2026-08-06 に登録・手動実行で成功を確認）
- 更新: 2026-08-06

## 何を解決するのか

公開後の取り込みは、**止まっても誰も気付かない**。

画面はエラーにならない。レースボードは表示され、予想も出る。ただし中身が古い。
利用者から見れば「今週のレースが出てこない」だけで、壊れているようには見えない。
運用側も、見に行かない限り分からない。

**「動かす」ことより「止まったと気付く」ことが設計の主題**なのはこのため。
実行の自動化だけを入れると、失敗したときに沈黙する仕組みが1つ増える。

## 全体像

```
[Windows機]                          [Cloud Run]        [GitHub Actions]
 タスクスケジューラ
   └ sync_mykeibadb.bat
       └ mykeibadb.exe  (JV-Link → MySQL)
       └ batch.py       (MySQL → API) ──HTTP──► /internal/ingest/*
                                                   └ ingest_log へ記録
                                                                    毎日 ┌──────────┐
                                                 /api/v1/ingest-status ◄─┤ 鮮度の確認 │
                                                                        └─────┬────┘
                                                                     異常なら失敗
                                                                              ▼
                                                                        所有者へ通知
```

3層に分ける。**どの層が落ちても最後の層が気付く**ようにするのが要点。

| 層 | 役割 | 実体 | 状態 |
|---|---|---|---|
| 実行 | 週次で取り込む | Windows タスクスケジューラ | 登録済み |
| 記録 | 成否を残す | `ingest_log` テーブル | 実装済み |
| 検知 | 止まったら知らせる | GitHub Actions 定期実行 | 実装済み |

## 実行層（Windows タスクスケジューラ）

`apps/ingestion-worker/scripts/setup_task_scheduler.ps1` を管理者権限で実行して登録する。

スケジュールは **JRA の発表時刻から逆算**している（推測ではない）。
出典: https://jra.jp/faq/pop02/2_2.html

| 発表されるもの | 時刻 |
|---|---|
| 枠番**なし**の出馬表 | 木曜16時すぎ |
| 枠番**あり**の出馬表 | **レース前日**の10時すぎ |
| 一部重賞・G1 | 木14時 / 金9時 すぎ（例外） |

**最も間違えやすいのは「レース前日」の意味。** 土曜のレースは金曜、
**日曜のレースは土曜**に枠順が出る。金曜だけ取り込む形にすると、
**日曜のカードが土曜まで丸ごと入らない**。実際 2026-08-07（金）の時点で、
画面は「8月8日 36R / 8月9日 0件」だった。異常ではなく発表前だっただけ。

JRA 自身が「表示できるまでに多少時間（約15分程度）がかかります」と注記している。
**10時は下限であって開始時刻ではない。** 実測でも 10:00 ちょうどの実行では
特別登録の9件しか取れず、同日 12:03 の実行で36レース全部が入った。

| 曜日 | 時刻 | 取るもの |
|---|---|---|
| 火 | 21:00 | 月曜発表の特別登録 |
| 木 | 17:00 | 枠番なしの出馬表（木16時すぎ） |
| 金 | 11:00 | **土曜の枠順**（金10時すぎ） |
| 金 | 13:00 | 11:00の保険 |
| 土 | 11:00 | **日曜の枠順**（土10時すぎ） |
| 土 | 13:00 | 11:00の保険 |
| 土 | 21:00 | 土曜の結果 |
| 日 | 21:00 | 日曜の結果 |

**回数を決めているのは反映の速さであって、完全性ではない。** 各実行は
「10日前〜先」のウィンドウをなめ直すので、1回飛んでも次が拾う。追加は安全側。

11:00 と 13:00 の2段にしているのは、**配信ラグの正確な値を仕様として固定しない**ため。
JRA 側の都合で発表が前後しても、どちらかで拾える。

21:00 は最終レース確定（16:30頃）からの余裕であって、実測値ではない。
配信ラグはログで確かめる余地がある。

木曜17:00 で枠番なしの出馬表が取れるかは**未検証**。取れれば木曜夕方から
出走馬を見せられる。取れなくても他の回が拾うので害はない。

### 公開に伴って変わる設定

**ワーカーの接続先を Cloud Run へ向ける。** これまではローカルのAPIを叩いていた。

`apps/ingestion-worker/.env`:

```
API_BASE_URL=https://<Cloud Run のURL>
INGEST_TOKEN=<Cloud Run に設定したものと同じ値>
```

`INGEST_TOKEN` が食い違うと `/internal/ingest/*` が 401 を返す。
`batch.py` は送信失敗を終了コードへ反映するので、タスクは失敗として記録される。

**タスクの成功（`LastTaskResult: 0`）は「どこへ書いたか」を保証しない。** 接続先が
ローカルのままでも、手元のAPIが起動していれば成功で終わる。そのAPIが Supabase を
向いていればデータ自体は入るため、**自動化が手元のAPIの起動に依存していることに
気付けない**。閉じた瞬間から静かに失敗し始める。書き込み先は必ず公開APIの
`/api/v1/ingest-status` 側で確かめる（`scripts/check_ingest_freshness.py`）。

### リクエストの時間上限（2026-08-07 の障害）

`forecasts/precompute` が 504 で打ち切られ、取り込みが失敗した。

原因は2つが噛み合ったこと。**ワーカーは先14日分をまとめて1リクエストで送っており**
（週末2回分・70レース超）、**Cloud Run のリクエスト上限は 60 秒**だった。
ワーカー側のクライアント上限は 300 秒で、ホスティング側の上限を見ていなかった。

同時にレース一覧も 504 になった。長時間のリクエストが接続プール（1プロセス5本）を
握り続け、他のリクエストが待たされたためと見ている。**重い処理は自分のエンドポイント
だけでなくサービス全体を巻き込む。**

対処:

- ワーカーは**1日ずつ**送る（`PRECOMPUTE_CHUNK_DAYS`）。1リクエストが1開催日を
  超えないので、上限がいくつであっても収まる。途中で落ちてもそこまでは残り、
  次の実行が残りを拾う。
- Cloud Run の `--timeout` を 300s へ。`deploy-cloudrun.yml` も同じ値にした。
  **ここを下げると取り込みが静かに壊れる**（画面は古いまま表示され続ける）。

### 決めきれていないこと: ログオン状態への依存

現在の登録は `-LogonType Interactive` で、**そのユーザーがログオンしている間しか動かない**。
再起動して自動ログオンしない構成だと、以後ずっと動かないまま静かに止まる。

選択肢は2つ。

1. **ログオンしたまま運用する**（現状のまま）
   追加設定が要らない。再起動で止まるが、**検知層が翌日には気付く**ので致命傷にならない。
2. **「ユーザーがログオンしていなくても実行する」に変える**
   アカウントのパスワードを Windows に保存する必要がある。確実だが、個人PCで
   パスワードを預ける判断が要る。

**当面は 1 で十分**と判断している。検知層がある前提なら、止まったことは翌日に分かる。
無人運用へ移す段階で 2 を検討する。

## 記録層（`ingest_log`）

`batch.py` が工程ごとに成否を書く。`/api/v1/ingest-status` がここを集計して、
最終成功時刻・経過日数・直近の失敗・鮮度判定を返す。

トップ画面の「データは最新です」の帯も同じ情報源。**画面と監視で判断がずれない**。

## 検知層（GitHub Actions）

`.github/workflows/monitor-ingest.yml` が毎日 12:00 JST に
`apps/api/scripts/check_ingest_freshness.py` を実行する。

異常なら**ワークフローを失敗させる**。GitHub が定期実行の失敗を所有者へメールで通知するため、
これだけで通知経路になる。追加のサービスも費用も要らない。

ログに出すだけにしないのは、誰も見ないから。**失敗という形にして初めて届く。**

判定条件:

- 取り込みの履歴が無い（ワーカーがAPIへ一度も届いていない）
- 直近の取り込みが失敗している
- APIが鮮度不足と判定している（`is_stale`）
- 最終成功から `--max-days`（既定4日）を超えた

4日にしているのは、金土日の周期に対して1周期分の余裕を見た値。開催の無い週でも
特別登録の取り込みが動くので、更新自体は途切れない。

### 設定するもの

| 種別 | 名前 | 値 |
|---|---|---|
| Variables | `PUBLIC_API_BASE_URL` | Cloud Run のURL |
| Secrets | `PUBLIC_API_TOKEN` | API に設定したものと同じ値 |

未設定ならワークフローは**スキップして成功で終わる**。失敗させると毎日通知が飛び、
本当の異常に気付けなくなるため。

## 今後の選択肢

**Cloud Run 側へ寄せる案は採らない。** JV-Link は Windows 専用の COM で、
`mykeibadb.exe` も Windows でしか動かない。取り込みの起点は Windows 機に残さざるを得ない
（ADR-0002）。

将来的に検討しうるのは、**Windows機が「取りに行く」形から「送るだけ」へ寄せる**こと。
取り込みの起動を Cloud Run 側のスケジューラから叩ければ、実行時刻の管理が1か所に寄る。
ただし Windows 機を外部から叩ける状態にする必要があり、家庭内ネットワークでは割に合わない。
**現状の「Windows機が能動的に送り、外から鮮度を見張る」形が、構成に対して素直**と考えている。
