# DECISIONS — 設計判断ログ

> 「後で覆すと高コスト」な決定は `docs/adr/` に MADR 形式で起票すること（ここには要約とリンクのみ）。

## 2026-07-12 隊列予想は枠順確定後だけ4ゾーンで表示する

- **背景**: 特別登録馬にも取り込み時の仮馬番が付くため、馬番の有無だけでは枠順確定を判定できない。
  また、現行データにはゲートの出脚を直接表す値がなく、厳密な一列順を断定する根拠が不足している。
- **採用案**: 全馬の `frame_no` が1〜8、馬番が正かつ一意の場合のみ `formation-v1` を生成する。
  表示は「先頭・好位・中団・後方」の4ゾーンとし、脚質70%・近走序盤位置30%の仮係数を
  `FormationWeights` に隔離する。APIは未確定時 `formation=null`、Webはセクション非表示。
- **理由**: 特別登録の `frame_no=0` を利用すればDB移行なしで誤表示を防げる。ゾーン表示なら、
  スタート直後の入れ替わりを考慮しつつ、現在のデータが示せる確度を超えて断定しない。
- **不採用案**: `RaceStatus` に即座に `special_registered/draw_confirmed` を追加する案は、既存データの
  移行と取り込み契約変更が大きいためMVPでは見送る。馬番だけの判定は仮馬番を誤認するため不採用。
- **見直し条件**: 発走速度・テン位置の追加データが安定取得できた場合、または状態判定を他機能でも
  共用する必要が出た場合は、状態列の追加と隊列内順位の精緻化を再検討する。

## 2026-07-11 想定RPCI 受入基準の未達に対する当面の方針（追加投資しない）

- **背景**: 実DBバックテスト（`docs/SPEC.md §8`, ADR-0005 §5.4）で、MAE≤1.5 は構造的に未達
  （混合7.848/芝8.861/ダート8.332、15,440レース規模の過去計測とも整合）、展開ラベル一致率≥60% は
  芝(73.5%)・混合(61.0%)は達成、ダート(42.5%)は未達と判明。「未達なら要因追加」の判断が必要だった
  （design/07 C4）。ユーザーから推奨方針の提示・実行を依頼された。
- **採用案**: 現行モデル（lgbm-turf-v1 / lgbm-dirt-v1）のまま運用を継続し、**MAE≤1.5 を追いかける
  追加投資は今は行わない**。既存の予測フィードバックループ（`forecast_accuracy`、`9712fd2`）を
  実運用での継続監視の手段として使い、蓄積データが増えてから再評価する。
- **理由**:
  1. MAE の未達幅（目標の約5〜6倍）は2回の独立した計測（15,440レース規模・直近200レース×3パターン）
     で一貫しており、閾値調整等の小手先では埋まらない構造的な差と判断できる。
  2. UI には PCI/RPCI 実数値を出さない方針（PROJECT_RULES §5）のため、製品価値に直結するのは
     「ハイ/平均/スロー」ラベルの妥当性と PAI の順序（展開合致馬抽出）であり、MAE そのものではない。
     ラベル一致率は3分類ランダム(33%)を上回り、PAI リフトは track別に見れば
     1.18〜1.32x と一貫して正の効果を示している（希釈前の見かけの無相関に惑わされない）。
  3. ダート的中率42.5%・芝「平均」再現率14.3%はいずれも根本原因（特徴量不足かデータ量不足か）が
     未診断であり、原因を特定しないまま再学習・特徴量追加へ投資するのは非効率。
- **不採用案**:
  - 直ちに特徴量追加・学習データ拡張へ投資 → 根本原因未診断の段階では優先度が低いと判断し見送り。
  - 受入基準（MAE≤1.5）の数値自体をこの場で緩和・改定 → 受入基準はユーザー（プロダクトオーナー）が
    design/07 で定めたものであり、基準値の改定自体はこの決定の範囲外（`docs/SPEC.md §9` の
    未確定事項として残す。ここで決めたのは「今は追加投資しない」という運用方針のみ）。
- **見直し条件**: `forecast_accuracy` の蓄積が増える（track毎に100件超など）につれ、
  的中率が実測でさらに悪化する、またはダートの外れ方に偏り（例: 常にハイ側へ外す）が見えた場合は、
  ダート限定の特徴量追加を優先して再検討する。ユーザーの体感評価（実際に使ってみた印象）が
  この方針と食い違う場合も随時見直す。

## 2026-07-11 予測フィードバックループ（予測 vs 実績の答え合わせ）を確定後回顧に組み込む

- **背景**: 想定RPCI は mart 層 `predicted_pace` に保存済みだったが、確定後にそれを読み返す経路が無く、
  `MartRepository` に read メソッドすら無かった。ユーザー・開発者ともに「予想が当たったか」を確認できなかった。
- **採用案**: `MartRepository.find_predicted_pace()` を追加し、`GetPaceAnalysisUseCase` が optional な
  `mart_repo` 経由で想定RPCI を引き当て、`classify_pace`（バックテストと同一基準）で的中判定して
  API の `forecast_accuracy` と回顧コメントに反映。既存挙動は後方互換（未保存なら null）。
- **理由**: コアバリュー（非専門家が展開予想を信頼して使える）に直結。既存資産（predicted_pace 永続化・
  classify_pace・commentary）の自然な結線で実現でき、蓄積し始めた実データを活かせる。
- **不採用案**: 専用の accuracy テーブル/バッチを新設 → 現段階では過剰。まず read-time 比較で価値検証。
- **見直し条件**: 的中率の推移ダッシュボードや大量集計が要るフェーズになったら、
  accuracy の永続化・専用集計（backtest の DB 化）を検討。

## 2026-07-11 好走実績を隣接ペースレベルへ「にじませて」から正規化する

- **背景**: 好走が特定レベル（例: かなり落ち着いた流れ）に集中する馬が、隣接レベル（落ち着いた流れ）を
  「直接実績ゼロ=スコア0=不安」と誤判定し、実際は好走するケースが再発していた。
- **採用案**: `affinity.py` の集計段で、各好走の重みを直接隣接レベルへ 40%（`_NEIGHBOR_BLEED_RATIO`）
  配分してから正規化。2ホップ先には広げない。
- **理由**: `PaceSpeedLevel` は連続量の離散化であり、隣接は近い性質を持つ。「証拠がない=不適性」ではない。
- **不採用案**: 閾値/ラベル側で救済 → 根本原因（集計の独立正規化）を残すため不採用。
- **見直し条件**: 実データ検証で 0.4 が過大/過小と判明したら係数調整、または連続カーネルへ拡張。

## 2026-07-11 外部データの上がり3F 異常値を取り込み側で除外する

- **背景**: mykeibadb の一部レースで `KOHAN_3F` が物理的にあり得ない値（例 13.7秒）になっており、
  PCI 式を通して RPCI が 300 超になっていた。自コードの変換バグではなく元データ破損と確認。
- **採用案**: `parse_se_result` で上がり3F が 25.0〜55.0 秒の範囲外なら当該成績を採用しない（None 返し）。
  取消/不正タイムと同じ silent-skip パターン。
- **理由**: 計算式の単一の真実の場所（pci.py）を、どのクライアント由来でも壊れた入力から守る。
- **不採用案**: 逆算して「正しい」変換を推測 → 誤変換のリスクがあり不採用。
- **見直し条件**: 障害戦等で正当に範囲外になる事例が出たら範囲を再検討。

## 2026-07-11 Task Scheduler 自動化を mykeibadb 経路に切替（JV-Link 直叩きを断念）

- **背景**: 実行機の JV-Link COM が 32bit 専用登録で、64bit Python から利用不可。実運用は
  `mykeibadb.exe`（JV-Link→MySQL）+ `batch.py --mode mykeibadb` の2段構成だった。
- **採用案**: `mykeibadb.exe` 起動→`batch.py`（entries/results）を通しで実行する
  `run_mykeibadb_full_sync.ps1` を Task Scheduler（金/土 10:00・日 18:00）に登録。過去7日〜未来14日を対象。
- **理由**: JRA の枠順確定・特別登録の公開サイクルに合わせ、単日でなくレンジで取りこぼしを防ぐ。
- **不採用案**: JV-Link を Python から直接（32bit venv 再構築）→ 現状の運用ツールを活かす方が低コスト。
- **見直し条件**: JV-Link を直接叩く要件が出たら 32bit 環境を別途用意。

## 2026-07-11 自動実行スクリプトは純 ASCII で書く

- **背景**: Windows PowerShell 5.1 が BOM 無し UTF-8 を CP932 で誤読し、日本語コメントや `→` が
  変数名に混入してスクリプトがクラッシュした。
- **採用案**: Task Scheduler 用 `.ps1/.bat` は英語・純 ASCII のコメント/ログに統一。
- **理由**: 無人実行の信頼性を、特定の BOM/コードページ環境に依存させない。
- **見直し条件**: 実行系を PowerShell 7（UTF-8 既定）に固定できるなら日本語コメント可に緩和検討。
