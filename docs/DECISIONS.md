## 2026-07-21（3）統合順位予想 Phase 2完成: gradeを直接利用し、馬体重は永続化のみ

- **背景**: ユーザーがPhase 2残件の完成を指示。既存実装を確認すると、SEの馬体重は既存
  `race_entries.weight`へ保存されていた一方、results単独再取込では更新されず、gradeはRAパーサーが
  常にNoneを返していた。能力重みの実績比較指標も不足していた。
- **判断（grade）**: JRA-VAN JVData Ver.4.9.0.1の「2003.グレードコード」と既存仕様表の
  `GradeCD[615]`を使用。A/B/C/D/E/F/G/H/LをG1/G2/G3/重賞/特別/J・G1/J・G2/J・G3/Lへ変換し、
  `races.grade`へ保存する。ability-v3はgradeを優先し、欠損時だけrace_class推定へ縮退する。
- **判断（馬体重）**: 新規カラムは作らず、実態として馬体重を保持する既存`weight`を維持する。
  results契約にも確定馬体重を追加して再取込時に更新する。体格の大小を地力へ加点する根拠がないため、
  馬体重は能力スコアへ組み込まない。
- **判断（検証）**: バックテストへ1位馬勝率・1位馬好走率・TOP3好走捕捉率を追加する。
  `AbilityWeights`は引き続き暫定で、実DBの同一期間比較で改善が再現した場合だけ変更する。
- **見直し条件**: 実JV-Link COMのRAでGradeCD[615]を再確認する。馬体重変化と好走に再現性のある関係が
  確認できた場合は、体格の絶対値ではなく前走比・個体内変化として別成分化を検討する。

## 2026-07-21（2）統合順位予想: 印→タグUI・順位明確化＋Phase2（人気・本賞金→ability-v2）

- **背景**: Phase1 を見たユーザーから「◎○▲△の印よりタグ付き分類の方が分かりやすい」「順位付けを
  明確に」とフィードバック。加えて Phase2（能力指数の強化）実装の指示。
- **判断（UI）**: `IntegratedRankingView` を刷新。**◎○▲△の印を廃止**し、総合順位（1位,2位…）を
  左端の主役に、分類は**言葉タグ**（本命／対抗／穴（妙味）／人気でも注意／能力上位・中位／
  展開が向く・向きにくい）で表示。プレゼンテーション層のみの変更（ドメイン/スキーマは不変）。
  印は競馬玄人向け記法で、非専門家向けの本プロダクトにはタグの方が合致する。
- **判断（Phase2 データ）**: **人気(TANSHO_NINKIJUN)・獲得本賞金(KAKUTOKU_HONSHOKIN)** を永続化。
  馬体重(能力寄与小)・grade(本賞金で代替可＋RAオフセット未特定でリスク)は今回見送り。
  本賞金を選ぶ最大の理由: **「入着時の稼ぎ＝競走相手のクラス」を連続量で捉え、grade未永続化による
  クラス係数 best-effort の限界を直接埋める**から。
- **判断（Phase2 経路）**: mykeibadb 列 → SE合成レコードの**予約オフセット**（jv_spec
  `Ninki`[541:543]/`Honsyokin`[543:552]、末尾の未マップ領域）→ `parse_se_result`（妥当性ゲート付き）
  → Ingest API → `race_entries.popularity/prize_money`（migration 003）。**実 JV-Data のオフセットは
  未検証**のため mykeibadb 合成専用と明記し、jvlink 実 COM では書かれず読み側で弾く（§9-8 と同方針）。
- **判断（ability-v2）**: form(近走着順×クラス)0.55 + 本賞金(対数正規化)0.30 + 人気0.15 を新しさ加重で
  ブレンド。**データが無い成分は除外し重みを再正規化** → 旧データ（人気/賞金なし）は form のみ＝v1 相当へ
  **安全に縮退**（再取込するまで壊れない）。重みは🧪暫定（§9-16）。
- **不採用案**: 印を残しつつタグを併記 → 情報過多。単一総合スコアで順位のみ → Phase1で不採用済み。
  grade を RA から永続化 → バイトオフセット未特定で実データ検証が要り、本賞金で目的を代替できる。
- **見直し条件**: ユーザーが migration 003 適用＋過去成績再取込（`MANUAL_SYNC_GUIDE §7.5`）した後、
  能力指数の的中傾向を実データで検証。重み・レンジを調整、必要なら馬体重/grade を追加（Phase2残）。

## 2026-07-21 統合順位予想（能力×展開）: 現データのみのPhase1・2軸分類を採用

- **背景**: ユーザー要望「展開＋絶対能力の統合順位予想」（2026-07-12に一旦保留）を再開。
  独断で仕様化しない方針に従い、能力指数の定義とデータ範囲・統合の見せ方をユーザーに選択提示した。
- **判断（採用案）**:
  - データ範囲: **現データのみでPhase1**（ユーザー選択）。人気・オッズ・獲得賞金は未永続化のため使わず、
    core層にある finish_pos / field_size / race_class / race_date から能力指数(ability-v1)を作る。
    能力 = 「出走頭数で正規化した着順 × クラス係数」の新しさ加重平均（直近5走）。
  - 統合の見せ方: **2軸分類（◎本命/○対抗/▲穴/△危険）**（ユーザー選択）。能力の相対順位を主・
    展開適性(PAI)を従とし、能力上位×合致=本命/上位×中立=対抗/上位×不利=危険/中位×合致=穴 に分類。
    表示順も同2軸から決定的に導く。
- **理由**: まず動く最小版を早く出す方針。2軸分類は説明可能性・非専門家向けの価値に合致し、
  「人気だが危険（上位×不利）」「中位でも展開特注の穴」という妙味を明示できる。
- **不採用案**:
  - 先にingestion拡張して人気・賞金を永続化 → 着手が重く、まず価値検証を優先（Phase2へ）。
  - 能力とPAIを1本の重み付きスコアに合算した単一順位 → 合算係数が恣意的で「なぜこの順位か」の
    説明が弱くなるためユーザーが不採用。
- **既知の限界**: `grade` コードが未永続化（`parse_ra`がNone）のため、クラス係数は `race_class`
  文字列の best-effort 判定。条件名（未勝利/n勝/オープン/G1-3）は拾えるが、ステークス名のみの重賞は
  中立化される。現段階の能力指数は事実上「クラス補正付きの近走充実度」。
- **見直し条件**: 実データで能力上位の的中傾向を検証。精度が物足りなければ Phase2（人気・賞金・
  馬体重の永続化）へ。`AbilityWeights`（🧪仮係数）は検証後に確定（`docs/SPEC.md §9`-16）。

## 2026-07-21 確定成績未反映は「解決」: 送信失敗をexit 0に握りつぶしていた欠陥を可視化

- **背景**: 2026-07-12以降、確定成績がアプリに反映されなかった件の決着。診断ツールで
  「解析は正常（453件解析可・DATA_KUBUN='7'）」と判明し、原因は解析より下流と特定できた。
- **判断**: `RecordRaceResultUseCase`はレース未登録で例外を投げるが、`batch.py`の`ingest_results`が
  それをper-raceで握りつぶし step は exit 0 にしていた（全送信失敗でも「成功・0件」に見える）。
  送信成功/失敗の件数ログ（「確定成績送信 …: 成功 X / 失敗 Y」・全滅時WARNING）を常設し、失敗を
  可視化。ユーザーが最新コードで results ステップを再実行→全レース送信成功しアプリに反映（解決）。
- **理由**: 旧状態は「自動同期の日付窓・実行状況＋可視性の欠如」が絡んだもので、パイプライン自体は
  正常だった。恒久対策は「例外を握りつぶさず件数で可視化する」こと（今回の再発防止の本質）。
- **見直し条件**: 障害競走の成績が別途未反映（ユーザー保留）。自動同期の実効監視（データ完全性の
  監視）は将来の改善候補（当初のクリティカル提案①、`tasks/backlog.md`）。

## 2026-07-20（2）確定成績未反映：exit codeだけのログを廃し、切り分け診断ツールを導入

> 追記（診断結果・決定的）: ユーザーが `diagnose_results` を実行した結果、**SE 1463行読込・
> 確定成績453件は正しく解析でき、生DATA_KUBUNも既に'7'**だった。すなわち「読み取り・解析」は
> 正常で、(B)列名不一致でも(C)バイト配置バグでもない。原因は**解析より下流＝APIへの送信/登録**。
> `RecordRaceResultUseCase`はレース未登録時に例外を投げ、`ingest_results`がそれをper-raceで
> 握りつぶしてexit 0にしていた（＝失敗が不可視）。対応として送信成功/失敗の件数ログと、
> 診断のRA突き合わせ（出走表未登録の検出）を追加。次はresultsログの送信件数で失敗理由を確定する。

- **背景**: 上の DATA_KUBUN 修正（`af922a5`）を投入してユーザーが再同期しても確定成績は反映されず、
  同期ログは `entries=0 results=0 special-entries=0` だった。この数字は**件数ではなく exit code**で、
  「クラッシュしていない」以上の情報が無い。そのため「SE行を1行も読めていない（mykeibadb未取得＝
  コード外）」のか「読めているが確定成績として解析できていない（コード内のバグ）」のかを
  区別できず、原因究明が完全に停滞した。レースは「成績未取込」一覧に出る＝entries側はSE行を
  読めているので、SE行自体は存在する（＝少なくとも「テーブルが空」ではない）ことだけは判る。
- **採用案**: 原因を推測で潰すのをやめ、**実データを測って切り分ける**方針へ転換。
  (1) `batch.py`に件数ログ（SE何行読込／確定成績何行解析／何レース記録）を常設し、以後の同期は
  それ自体が診断情報を残すようにする。(2) `ingestion.diagnose_results`を新設し、実DBのSE行について
  着順/タイム/上り3F列の有無・DATA_KUBUN分布・parse成功数・**SEテーブルの実列名一覧**を出力。
  これで (A)mykeibadb未取得 /(B)列名がパーサ候補と不一致 /(C)合成レコードのバイト配置バグ を
  一撃で切り分ける。(3) 副次的に`DaysBack`既定を7→10へ（月曜実行時に前々週土曜が日付窓から
  漏れる問題。7/12の欠落はこれで説明可能）。
- **理由**: 低可視性の環境（実DBに触れないクラウド側）で仮説を1つずつ投げて外し続けるのは高コスト。
  ユーザーに1回スクリプトを回してもらえば原因層が確定し、以後の修正が的を射る。DATA_KUBUN仮説の
  空振りは「測る前に直そうとした」ことが原因であり、同じ轍を踏まないための恒久的な計測を優先する。
- **不採用案**: DATA_KUBUN以外の仮説（列候補の追加等）を当て推量で重ねて再度ユーザーに再同期を
  依頼する案 → 外れれば往復がまた1回無駄になる。診断ツールで確定させてから動く方が速い。
- **見直し条件**: 診断出力が (A) を示せば mykeibadb.exe/JV-Link 設定側（コード外）の調査へ移り、
  本リポジトリ側の`diagnose_results`は運用診断ツールとして残す。(B)/(C) を示せば
  `mykeibadb_client`の列候補追加やバイト配置修正で対応し、その内容を実データ根拠付きで追記する。

## 2026-07-20 確定成績が1週間以上反映されない件を調査し、DATA_KUBUN の扱いを修正（→ 空振り確認済み）

> 追記（2026-07-20（2））: 本修正を投入してユーザーが再同期しても改善せず、この仮説は**外れ**
> （少なくとも単独の真因ではない）と確認された。修正自体は単調で無害なため残置。原因究明は
> 上記「(2)」の診断ツール導入へ引き継いだ。

- **背景**: ユーザー報告: 2026-07-12以降（7/12・7/18・7/19の3開催日）確定成績が一切反映されない。
  一方、直前に修正した`--step special-entries`は正常に機能し、7/25・26の特別登録は反映されている。
  つまり「取り込み自体は動いている」（entries・special-entriesは機能）が「確定成績の検出だけが
  機能していない」状態で、かつユーザーは修正版で再同期を実施済みにも関わらず改善しなかった
  （単発の実行失敗ではなく、再現性のある不具合と判断）。
- **調査**: `mykeibadb_client._build_se_record()`を確認。wmykeibadbが「列分解済みテーブル」で
  出力する環境（docstringに記載の通りこちらが一般的）では、着順・タイム・上り3Fの値をSEレコードの
  該当バイト位置へ無条件に書き込む一方、DataKubunバイト（`se_parser.parse_se_result`が'4'/'7'
  でのみ確定扱いする判定材料）は、`DATA_KUBUN`列が存在する場合その値をそのまま採用し、
  存在しない場合のみ着順・タイム・上り3Fの有無から'7'/'1'を推測していた。
  もし実際のmykeibadb環境で`DATA_KUBUN`列の値がJV-Data本来の確定コードを正しく反映しない
  （例: 常に'1'のまま等）場合、着順等のデータ自体は正しく書き込まれているにも関わらず、
  `parse_se_result`のDataKubunチェックで毎回`None`を返し続ける、という一貫した説明がつく。
  同種の「列名/値の不一致で確定成績が全件消える」不具合は
  `test_iter_se_records_parses_results_from_wmykeibadb_columns`のコメントに過去の回帰として
  記録されており、今回はその変種（列名ではなく値の意味の不一致）と考えられる。
- **採用案**: `_build_se_record()`で、着順・タイム・上り3Fが全て揃っている場合は`DATA_KUBUN`列の
  値に関わらずDataKubunを'7'（確定）とする。全て揃っていない場合のみ、従来通り`DATA_KUBUN`列の値
  （無ければ'1'）を使う。この優先順位の変更は単調（monotonic）: 揃っているのに'7'にならなかった
  ケースだけを追加で確定扱いにし、揃っていない行を誤って確定扱いにすることはない。
  `parse_se_result`側の着順妥当性チェック（1〜98の範囲外は`None`）は独立して残るため、
  中止・失格馬（着順99等）を誤確定させる副作用もない。
- **理由**: entries/special-entriesが機能している以上、mykeibadb.exe/wmykeibadb自体は
  データを取得できていると考えられ、原因はPCI_app側のコード（DataKubunの解釈）にある可能性が
  最も高いと判断。同種の過去回帰の存在も仮説を補強する。
- **不採用案**: mykeibadb.exe/wmykeibadb側（このリポジトリのコード外）の不具合を疑い静観する案
  → entries/special-entriesが動いている事実と整合しない。まずコード側で説明可能な仮説から潰す。
- **見直し条件（重要）**: **この修正は実DBでの検証ができていない**。このクラウド環境から
  mykeibadbの実データ・実スキーマにアクセスできないため、`DATA_KUBUN`列の実際の値が本当に
  不整合を起こしているかどうかは確認できていない。ユーザーが本修正を反映して再同期し、
  確定成績が反映されるようになるかで検証する。直らない場合はこの仮説が誤りで、
  mykeibadb.exe/wmykeibadb側の同期失敗（このリポジトリのコード外）を疑う必要がある。

## 2026-07-13 展開恩恵馬カードの馬番表示に frame_no ガードを追加

- **背景**: ユーザーがスクリーンショットで報告: 枠順確定前（特別登録段階）のレースで、
  展開予想画面の「展開恩恵馬TOP5」「評価を下げたい馬」カードに馬番が表示されていた。
  調査の結果、`formation-v1`（隊列予想）は既に `frame_no`（枠番）で確定/未確定を判定し
  未確定時は `formation: null` を返す設計だったが、同じ画面の PAI 系出力
  `HorseFitOutput`/`HorseFitSchema` にはそもそも `frame_no` フィールドが無く、
  この判定が一切されていなかったと判明。特別登録段階の `horse_no` は
  `ingest_entries()` が UMABAN=0 のときに割り当てる暫定連番（実際の公式馬番ではない）
  であるため、これをそのまま「馬番 N」と表示するのは確定情報であるかのような誤解を招く。
- **採用案**: `HorseFitOutput`/`HorseFitSchema` に `frame_no: int` を追加
  （`FormationHorseSchema`と異なり `ge=1, le=8` の制約は付けない。0=未確定が正常値のため）。
  `forecast_use_cases.py` で `RaceEntry.frame_no` から `frame_no_by_no` マップを作り、
  `HorseFitOutput` 構築時に流し込む。web側は `lib/pace.ts` に `horseNumberLabel()` を新設し、
  `frame_no>0` なら「馬番 N」、`frame_no=0` なら「登録順 N（馬番未確定）」を返す。
  `RaceForecastDashboard.tsx`（TOP5カード・評価下げカード・先導候補チップ）、
  `HorseFitTable.tsx`、`app/page.tsx`（トップ画面の中心候補プレビュー）の計5箇所を統一。
  PAIスコア自体は枠順確定前でも意味があるため、formation-v1のように出力ごと非表示にはせず、
  ラベルの誠実さだけを是正する方針とした。
- **理由**: `RaceEntry`ドメインエンティティは既に`frame_no`を持ち、`formation-v1`が既に同じ
  判定基準（`has_confirmed_draw`）を確立していたため、新しい判定ロジックを作らず既存の
  「frame_no=0→未確定」という規約に揃えるのが一貫性が高い。
- **不採用案**: 枠順未確定時はPAI系カード自体を非表示にする案 → 展開恩恵馬の推薦は枠順確定前
  （特別登録段階）でも脚質ベースの分析として意味を持つため、情報自体を隠すのは過剰と判断。
  ラベルの表現だけを修正する方が実用的。
- **未対応（既知の残課題）**: `scenario.py`が生成する自然文コメント（`headline`/`detail`/
  `reasons`内の「馬番 N」等）は同種の問題が残る。`HorsePaceProfile`/`PaiResult`にframe_no相当が
  無く、対応にはdomain層の拡張が必要なため今回は対象外（`docs/SPEC.md §9`-14に記録）。
  露出箇所は「判定根拠データ」アコーディオン内に限られ、スクリーンショットで報告された
  箇所（常時表示のカード）とは異なる。

## 2026-07-13 自動同期スクリプトに `--step special-entries` 呼び出しを追加

- **背景**: ユーザー報告「月曜なのに土日の開催結果と来週の特別登録馬が反映されていない」を調査。
  `run_mykeibadb_full_sync.ps1`（Task Scheduler「PCI_Sync_Mykeibadb」金/土10:00・日18:00が実行）の
  中身を確認したところ、`batch.py --mode mykeibadb --step entries` と `--step results` のみを
  呼んでおり、`--step special-entries`（`ingest_mykeibadb_special_entries()`、mykeibadbの
  `TOKUBETSU_TOROKUBA`/`TOKUBETSU_TOROKUBAGOTO_JOHO` という**別テーブル**を読む独立ステップ）を
  一度も呼んでいなかったと判明。`setup_task_scheduler.ps1` 自身のdocstringには「日曜18:00は
  土日の結果に加え、来週の重賞特別登録の取り込みも兼ねる」と明記されていたため、これは意図的な
  仕様ではなく実装漏れ（2026-07-11のTask Scheduler自動化切替時に、entries/resultsのみ実装して
  special-entriesの追加を忘れたと推測される）。
- **採用案**: `run_mykeibadb_full_sync.ps1` に3番目の呼び出し
  `& $RunBatch -Step special-entries -Mode mykeibadb -Date $DateFrom -DateTo $DateTo`
  を追加（entries/resultsと同じ過去7日〜未来14日の日付窓を流用）。`sync_mykeibadb.bat`・
  `MANUAL_SYNC_GUIDE.md`（0節説明・1節手順・2節コマンド例・6.8節トラブルシューティング新設）・
  `docs/SPEC.md §6` を合わせて更新。
- **理由**: `--step special-entries` 自体は既にbatch.py/mykeibadb_client.pyで実装・単体テスト
  済みの機能で、`run_batch.ps1`のリトライ/Webhook通知も汎用的に対応済みだった。抜けていたのは
  自動実行スクリプトからの呼び出しのみで、日付窓の設計変更等は不要な低リスクな追加。
- **不採用案**: 特別登録専用の別スケジュール（例: 毎日実行）を新設する案 → 現状の金/土/日の
  週3回で「来週の特別登録」を捕捉するには十分な頻度と判断し、既存スケジュールへの追加のみとした。
  必要になれば`DaysForward`パラメータや専用トリガーを別途検討する。
- **見直し条件**: 今回の追加後も特別登録の反映漏れが再発する場合、日付窓（過去7日〜未来14日）が
  グレード較走の登録タイミングに対して不十分でないか確認する。
- **未解決**: 「土日の確定成績が反映されていない」側は、自動実行自体が失敗/未発火していた
  可能性がある（Task Scheduler実行履歴・ログ・MySQL80サービス状態はこのクラウド環境から
  確認不可）。ユーザー自身による診断が必要（`MANUAL_SYNC_GUIDE.md §6.8`参照）。

## 2026-07-12 取り込み鮮度を新規ドメイン`domain/ops`で監視する

- **背景**: `ingest_log` はバッチ実行の監査ログとして書き込まれるが、読み返す手段が無く、
  Task Scheduler が静かに失敗し続けても（過去に実際MySQL停止・文字化けクラッシュ等で発生）
  ユーザーが気づく手段が無かった。「監視強化」の最優先候補として着手。
- **採用案**: `ingest_log` は「pace」（PCI等の算出）とも「racing」（レース/馬）とも異なる
  運用監査データのため、新規に `domain/ops/` パッケージを作り `IngestLogRepository` Protocol と
  純粋関数 `evaluate_freshness()` を置く。判定は (a) 直近試行が失敗していないか、
  (b) 直近成功からの経過日数のみで、Task Scheduler の具体的なcron（金/土/日）は
  ハードコードしない（運用変更に強くするため）。`GET /api/v1/ingest-status`
  （`/internal/ingest/*` とは別の公開GET）で公開し、web トップに `IngestStatusBanner` で表示。
- **理由**: 既存の `mart_repository.py`（domain/pace/）と同様、Repository Protocolを domain 層に
  置くことで application 層が SQLAlchemy を知らずに済む（既存レイヤ規約の踏襲）。
  cronスケジュールを判定条件に埋め込まない設計により、スケジュール変更時のコード修正を避ける。
- **不採用案**: `RaceModel` に `updated_at` 等を追加して鮮度を推定する案 → 取り込みパイプライン
  自体の成否ではなくデータ内容の鮮度しか分からず、目的（パイプライン監視）とズレるため不採用。
  health エンドポイントへの相乗り → API サーバー死活と取り込みパイプライン死活は別関心事のため
  混在させず新規エンドポイントに分離。
- **見直し条件**: `STALE_AFTER_DAYS=4` は仮値（`docs/SPEC.md §9`-13）。しばらく運用し、
  誤警告（実際は正常なのに stale 表示）や見逃し（実際は異常なのに気づけない）が無いか確認する。

## 2026-07-12 脚質別有利度をドメインで算出する（web の最大PAI流用を廃止）

- **背景**: UI「展開分析」の脚質別有利度が 60〜96 に高止まりし差が出ない、とユーザーから指摘。
  原因は web 側が「その脚質に属する馬の最大PAI」を有利度として流用していたこと。これは
  「脚質内の最良馬の適性」であって「脚質自体が今回の流れで有利か」ではなく、二重に不適切だった。
- **採用案**: domain に `style_advantage.py`（style-advantage-v1）を新設。想定RPCIの中立点
  （`classify_pace` と同じ rule-v4 閾値の中点: 芝50/ダート43）からの乖離を、50=互角の対称スコアへ
  線形写像する。逃げ・追込は増幅率1.2で外側に振れ、逃げ候補2頭以上なら逃げのみ競合減点。
  `reasons`・`model_version` 付き。webは `styleAdvantageScores`（lib/pace.ts）で言葉ラベル
  （有利/やや有利/互角/やや不利/不利）を付けて表示するだけの翻訳層に戻した。
- **理由**: 有利度の本質は「想定ペースの方向」であり、その情報は predicted_rpci が既に持っている。
  中立点を classify_pace と共有することで、ペース3分類と有利度の判定基準がズレない。
- **不採用案**: web側で PAI の正規化を工夫して差を広げる → 「脚質自体の有利さ」ではない根本問題が
  残るため不採用。脚質別の平均PAIを使う → 出走構成に依存し、同じ想定ペースでも値が揺れるため不採用。
- **見直し条件**: `StyleAdvantageWeights` は仮係数（SPEC §9-11）。実績RPCIベースで有利判定脚質の
  好走率リフトを検証し調整する。ユーザーの体感（差が出過ぎ/出なさ過ぎ）でも随時調整。

## 2026-07-12 混在型の脚質だけを対象距離に応じて具体化する

- **背景**: 枠順確定済み直近20レース（266頭）で「自在」が139頭（52.3%）を占めた。
  内訳は、過去位置取りが複数脚質に分散して60%閾値へ届かない馬が99頭、履歴なしが40頭だった。
- **採用案**: 従来判定で逃げ・先行・差し・追込が確定する馬は変更しない。混在して自在となる馬だけ、
  過去5走の4角位置を対象距離への近さと新しさで重み付けする `running-style-v2-distance` を適用する。
  先行と差しが同数なら、先行歴が今回より短距離中心なら先行、長距離中心なら差しへ寄せる。
- **理由**: 全体の60%閾値を下げると明確な脚質の意味まで変わる。今回向け予測だけを別モデルとして
  分離すれば、確定済み成績の脚質定義を保ちつつ、隊列予想に必要な具体性を増やせる。
- **不採用案**: 履歴のない馬を枠番だけで具体化する案は根拠不足のため不採用。従来の自在をすべて
  一律に先行または差しへ振る案も、馬ごとの差を失うため不採用。
- **結果**: 同じ266頭で自在は40頭（15.0%）へ減少。残る40頭は履歴なしとして「参考」を維持する。
- **見直し条件**: 距離重み、近走減衰、先行距離補正は仮係数。十分な予想・結果ペアが蓄積したら、
  隊列ゾーン一致率で評価して更新する。

## 2026-07-12 隊列予想は枠順確定後だけ4ゾーンで表示する

- **背景**: 特別登録馬にも取り込み時の仮馬番が付くため、馬番の有無だけでは枠順確定を判定できない。
  また、現行データにはゲートの出脚を直接表す値がなく、厳密な一列順を断定する根拠が不足している。
- **採用案**: 全馬の `frame_no` が1〜8、馬番が正かつ一意の場合のみ `formation-v1` を生成する。
  表示は「先頭・好位・中団・後方」の4ゾーンとし、脚質70%・近走序盤位置30%の仮係数を
  `FormationWeights` に隔離する。APIは未確定時 `formation=null`、Webはセクション非表示。
- **理由**: 特別登録の `frame_no=0` を利用すればDB移行なしで誤表示を防げる。ゾーン表示なら、
  スタート直後の入れ替わりを考慮しつつ、現在のデータが示せる確度を超えて断定しない。
- **不採用案**: `RaceStatus` に即座に `special_registered/draw_confirmed` を追加する案は、既存データの
  移行と取り込み契約変更が大きいためMVPでは見送る。馬番だけの判定は仮馬番を誤認するため不採用。
- **見直し条件**: 発走速度・テン位置の追加データが安定取得できた場合、または状態判定を他機能でも
  共用する必要が出た場合は、状態列の追加と隊列内順位の精緻化を再検討する。

## 2026-07-11 想定RPCI 受入基準の未達に対する当面の方針（追加投資しない）

- **背景**: 実DBバックテスト（`docs/SPEC.md §8`, ADR-0005 §5.4）で、MAE≤1.5 は構造的に未達
  （混合7.848/芝8.861/ダート8.332、15,440レース規模の過去計測とも整合）、展開ラベル一致率≥60% は
  芝(73.5%)・混合(61.0%)は達成、ダート(42.5%)は未達と判明。「未達なら要因追加」の判断が必要だった
  （design/07 C4）。ユーザーから推奨方針の提示・実行を依頼された。
- **採用案**: 現行モデル（lgbm-turf-v1 / lgbm-dirt-v1）のまま運用を継続し、**MAE≤1.5 を追いかける
  追加投資は今は行わない**。既存の予測フィードバックループ（`forecast_accuracy`、`9712fd2`）を
  実運用での継続監視の手段として使い、蓄積データが増えてから再評価する。
- **理由**:
  1. MAE の未達幅（目標の約5〜6倍）は2回の独立した計測（15,440レース規模・直近200レース×3パターン）
     で一貫しており、閾値調整等の小手先では埋まらない構造的な差と判断できる。
  2. UI には PCI/RPCI 実数値を出さない方針（PROJECT_RULES §5）のため、製品価値に直結するのは
     「ハイ/平均/スロー」ラベルの妥当性と PAI の順序（展開合致馬抽出）であり、MAE そのものではない。
     ラベル一致率は3分類ランダム(33%)を上回り、PAI リフトは track別に見れば
     1.18〜1.32x と一貫して正の効果を示している（希釈前の見かけの無相関に惑わされない）。
  3. ダート的中率42.5%・芝「平均」再現率14.3%はいずれも根本原因（特徴量不足かデータ量不足か）が
     未診断であり、原因を特定しないまま再学習・特徴量追加へ投資するのは非効率。
- **不採用案**:
  - 直ちに特徴量追加・学習データ拡張へ投資 → 根本原因未診断の段階では優先度が低いと判断し見送り。
  - 受入基準（MAE≤1.5）の数値自体をこの場で緩和・改定 → 受入基準はユーザー（プロダクトオーナー）が
    design/07 で定めたものであり、基準値の改定自体はこの決定の範囲外（`docs/SPEC.md §9` の
    未確定事項として残す。ここで決めたのは「今は追加投資しない」という運用方針のみ）。
- **見直し条件**: `forecast_accuracy` の蓄積が増える（track毎に100件超など）につれ、
  的中率が実測でさらに悪化する、またはダートの外れ方に偏り（例: 常にハイ側へ外す）が見えた場合は、
  ダート限定の特徴量追加を優先して再検討する。ユーザーの体感評価（実際に使ってみた印象）が
  この方針と食い違う場合も随時見直す。

## 2026-07-11 予測フィードバックループ（予測 vs 実績の答え合わせ）を確定後回顧に組み込む

- **背景**: 想定RPCI は mart 層 `predicted_pace` に保存済みだったが、確定後にそれを読み返す経路が無く、
  `MartRepository` に read メソッドすら無かった。ユーザー・開発者ともに「予想が当たったか」を確認できなかった。
- **採用案**: `MartRepository.find_predicted_pace()` を追加し、`GetPaceAnalysisUseCase` が optional な
  `mart_repo` 経由で想定RPCI を引き当て、`classify_pace`（バックテストと同一基準）で的中判定して
  API の `forecast_accuracy` と回顧コメントに反映。既存挙動は後方互換（未保存なら null）。
- **理由**: コアバリュー（非専門家が展開予想を信頼して使える）に直結。既存資産（predicted_pace 永続化・
  classify_pace・commentary）の自然な結線で実現でき、蓄積し始めた実データを活かせる。
- **不採用案**: 専用の accuracy テーブル/バッチを新設 → 現段階では過剰。まず read-time 比較で価値検証。
- **見直し条件**: 的中率の推移ダッシュボードや大量集計が要るフェーズになったら、
  accuracy の永続化・専用集計（backtest の DB 化）を検討。

## 2026-07-11 好走実績を隣接ペースレベルへ「にじませて」から正規化する

- **背景**: 好走が特定レベル（例: かなり落ち着いた流れ）に集中する馬が、隣接レベル（落ち着いた流れ）を
  「直接実績ゼロ=スコア0=不安」と誤判定し、実際は好走するケースが再発していた。
- **採用案**: `affinity.py` の集計段で、各好走の重みを直接隣接レベルへ 40%（`_NEIGHBOR_BLEED_RATIO`）
  配分してから正規化。2ホップ先には広げない。
- **理由**: `PaceSpeedLevel` は連続量の離散化であり、隣接は近い性質を持つ。「証拠がない=不適性」ではない。
- **不採用案**: 閾値/ラベル側で救済 → 根本原因（集計の独立正規化）を残すため不採用。
- **見直し条件**: 実データ検証で 0.4 が過大/過小と判明したら係数調整、または連続カーネルへ拡張。

## 2026-07-11 外部データの上がり3F 異常値を取り込み側で除外する

- **背景**: mykeibadb の一部レースで `KOHAN_3F` が物理的にあり得ない値（例 13.7秒）になっており、
  PCI 式を通して RPCI が 300 超になっていた。自コードの変換バグではなく元データ破損と確認。
- **採用案**: `parse_se_result` で上がり3F が 25.0〜55.0 秒の範囲外なら当該成績を採用しない（None 返し）。
  取消/不正タイムと同じ silent-skip パターン。
- **理由**: 計算式の単一の真実の場所（pci.py）を、どのクライアント由来でも壊れた入力から守る。
- **不採用案**: 逆算して「正しい」変換を推測 → 誤変換のリスクがあり不採用。
- **見直し条件**: 障害戦等で正当に範囲外になる事例が出たら範囲を再検討。

## 2026-07-11 Task Scheduler 自動化を mykeibadb 経路に切替（JV-Link 直叩きを断念）

- **背景**: 実行機の JV-Link COM が 32bit 専用登録で、64bit Python から利用不可。実運用は
  `mykeibadb.exe`（JV-Link→MySQL）+ `batch.py --mode mykeibadb` の2段構成だった。
- **採用案**: `mykeibadb.exe` 起動→`batch.py`（entries/results）を通しで実行する
  `run_mykeibadb_full_sync.ps1` を Task Scheduler（金/土 10:00・日 18:00）に登録。過去7日〜未来14日を対象。
- **理由**: JRA の枠順確定・特別登録の公開サイクルに合わせ、単日でなくレンジで取りこぼしを防ぐ。
- **不採用案**: JV-Link を Python から直接（32bit venv 再構築）→ 現状の運用ツールを活かす方が低コスト。
- **見直し条件**: JV-Link を直接叩く要件が出たら 32bit 環境を別途用意。

## 2026-07-11 自動実行スクリプトは純 ASCII で書く

- **背景**: Windows PowerShell 5.1 が BOM 無し UTF-8 を CP932 で誤読し、日本語コメントや `→` が
